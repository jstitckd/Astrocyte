Astrocyte / Team handbook / 01

Know your way
around the code.

A practical guide to the project structure, how the pieces connect, and which file to edit for each change.

Astrocyte is a Python, Streamlit and Plotly website with a custom HTML/CSS/JavaScript Mars-base map. The code separates screens, reusable interface elements, data logic and visual styling so teammates can work independently.

Astrocyte/
├── app.py                    App startup and screen selection
├── views/                    Complete screen layouts
├── components/               Reusable interface elements
├── frontend/                 Illustration, CSS and JavaScript
├── models/                   Shared metric and building definitions
├── services/                 Data processing and session storage
├── data/                     Downloadable synthetic sample CSV
├── tests/                    Automated checks
├── docs/                     Technical and collaboration guides
├── .streamlit/config.toml    Streamlit theme and settings
├── requirements.txt          Required Python packages
└── Astrocyte.code-workspace  VS Code interpreter and debugger

How the app starts

app.py connects everything. It loads the styling, creates the session store, renders the sidebar and displays the selected view. It also shows the simulated/imported data indicator and footer.

1 Start app.py with Streamlit.

2 The sidebar chooses the dataset, crew member and dates.

3 A view receives those selections and builds the screen using components.

4 Services validate data and save the session’s workflows.

Keep the entry point small. Changes to app.py can affect the whole website. Agree who integrates shared changes before editing it simultaneously.

Astrocyte / Screens & interface / 02

What appears on screen.

Views assemble complete screens. Components supply the reusable pieces inside them.

views/ — screen layouts

FILEWHAT IT AFFECTS
views/home.pyHomepage title, introduction, map placement, summary cards and progress. Handles navigation after a building is selected.
views/dashboard.pyShared layout for all six health dashboards: measurement cards, chart, form, checklist and previous entries.
views/data.pyData & exports screen, sample download, accepted-format table and export buttons.
Six dashboards share one layout. Their different measurements and tasks come from models/areas.py. A change to views/dashboard.py can affect every dashboard.

components/ — reusable interface elements

FILEWHAT IT AFFECTS
sidebar.pyLogo, sidebar navigation, CSV uploader, crew selection and date filters.
base_map.pyPython connection to the HTML map; sends building names and tasks into it.
readings.pyLatest-reading cards and Plotly measurement graphs.
forms.pySymptoms, exercise, nutrition, wellbeing and observation forms; check-in history.
tasks.pyTask checkboxes, progress calculations and the editable EVA checklist.
context.pyThe ViewContext object carrying the selected crew, dates, readings and storage handle into views.

Example: clicking the sleeping quarters

map.js sends "sleep" → base_map.py receives it → services/navigation.py validates it.

views/home.py updates the selected page → app.py displays views/dashboard.py for "sleep".

The sidebar uses the same building IDs, so people can reach every dashboard without interacting with the map.

Astrocyte / Data & storage / 04

What happens behind the interface.

Services process data and manage session workflows. Measurements and self-reported entries stay separate.

services/ — application behaviour

FILEWHAT IT AFFECTS
services/ingestion.pyCSV parsing, validation, crew/date filtering and reading exports.
services/demo.pyGenerates the synthetic measurements shown in Demo mission.
services/storage.pySaves imports, check-ins, task completion and custom EVA lists in session memory; creates JSON exports.
services/navigation.pyRejects invalid or repeated map navigation events.
services/adapters.pyDefines the interface for a future wearable or API provider. No provider is currently connected.

Two separate data paths

Measurements
CSV / demo → validation → crew and date filtering → cards and charts.

Self-reported entries
Forms → check-in validation → session storage → history and JSON export.

The sidebar applies filters and passes a ViewContext to the current view. Check-ins and task completion are scoped to the selected dataset, crew member, date and area. Saving a check-in does not overwrite measurement rows.

data/ — the sample import file

data/sample_readings.csv is the safe, synthetic example available for download and upload.

Editing the CSV does not change Demo mission. Demo readings come from services/demo.py. Change the generator to change the demo, then regenerate the sample so both match. The regeneration command is in docs/data-contract.md.

What persists?

storage.py currently keeps records in browser-session memory. Normal interactions and navigation preserve them, but a disconnect, refresh or restart can lose them. Nothing is saved to a shared database.

Export readings as CSV and session check-ins, tasks and custom EVA lists as JSON before disconnecting. The JSON export is an archive; a restore workflow is not implemented.

To add a real provider, follow the adapter interface and validate its output through the existing ingestion boundary. The demo requires no API credentials.
